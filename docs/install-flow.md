# Windows Arm Install Flow

> **This is an evidence log, not a setup guide.** It records dated findings from getting Windows 11 Arm to
> boot and reach the desktop under local QEMU/HVF — including the attempts that failed and why. Read it when
> a step is behaving unexpectedly and you want to know what was already tried.
>
> **For the ordered setup commands, see [First Run in the README](../README.md#first-run).**

Veil's install flow is designed around a bring-your-own Windows 11 Arm model. The product goal is not to hide licensing or media ownership. The goal is to make the setup path explicit, recoverable, and ready for a local runtime provider implementation.

## Product Intent

Users should not manage a generic VM app once setup is complete. They should prepare Windows once, install the Veil guest agent once, and then use Windows apps through the macOS host shell.

## v0.1 Setup Model

The macOS host stores a local VM profile and reports five setup steps:

1. Windows 11 Arm installer
2. Virtual disk
3. macOS shared folder
4. Automatic install media
5. Veil guest agent

The first four are local host prerequisites. The guest agent step remains pending until Windows can boot and the agent installer exists.

## Current Host Behavior

- Prepare VM creates the default Windows 11 Arm profile, the macOS shared folder at `~/Veil Shared`, and the default sparse disk in one action.
- Prepare VM does not scan Downloads or any other broad user folder for installer media. The user chooses the Windows ISO explicitly in the host app, or passes it through `veil-vmctl prepare --installer <path>`.
- Prepare VM creates `~/Veil Shared/Autounattend.xml` with Windows Setup language/OOBE inputs, Windows 11 Pro image selection, UEFI/GPT disk partitioning for the blank VM disk, an offline OOBE registry fallback, and no product key value.
- Prepare VM creates `~/Veil Shared/VeilAutoInstall.iso`, a small local ISO containing `Autounattend.xml` and, when available, the Veil guest-agent bootstrap payload. Veil only rebuilds this media when setup or guest-agent recovery payloads are needed and have changed.
- Prepare VM applies an adaptive resource profile from the current Mac: half of host CPU cores up to a safe cap, 25% of physical memory rounded down to a conservative VM cap, and a 128 GB default sparse disk.
- `veil-vmctl prepare --installer <path>` prepares the same local profile, shared folder, default sparse disk, installer path, and diagnostics bundle from the command line.
- `veil-vmctl prepare --installer <path> --drivers <path>` also stores an optional user-provided Windows driver ISO path. Veil attaches that media read-only during QEMU/HVF boots, but does not download, bundle, or license driver media.
- Profile-only creation is still available for low-level setup testing.
- Installer media is a user-selected local file. Veil stores the selected path and a security-scoped bookmark in the local profile, but does not copy, redistribute, or auto-discover Windows media.
- VM start resolves stored security-scoped bookmarks before file validation and local QEMU/HVF launch, reducing repeated macOS file-access prompts after the user has explicitly selected the ISO, driver media, or disk.
- If an older profile points at `~/Downloads` media without a stored security-scoped bookmark, Veil blocks boot readiness and asks the user to re-select the ISO in the app, or re-register it with the concrete `veil-vmctl prepare --installer ...` command surfaced in runtime diagnostics, instead of touching the protected Downloads path during snapshot loading.
- Snapshot loading also ignores stale QEMU console screenshots under `~/Downloads` so the app can open without macOS prompting for Downloads access; diagnostics should live under Veil's Application Support directory unless the user explicitly exports them.
- The virtual disk can be user-selected or created as a blank `qcow2` disk at `~/Virtual Machines/Veil/Windows 11 Arm.qcow2` (a raw sparse `Windows 11 Arm.img` when no `qemu-img` is available). Existing raw disks keep working; Configuration > Disk converts one to `qcow2` on request.
- The boot spike stores EFI variables and the generic machine identifier next to the virtual disk so repeated boots keep stable VM identity.
- The host now prefers the local QEMU/HVF compatibility provider when it is installed and ready, because that is the clearest path to a UTM-style visible Windows installer console. Apple Virtualization remains the fallback feasibility provider.
- While a QEMU/HVF VM is starting or running, the host shell quietly refreshes the latest VM-console screenshot through the recorded monitor socket so the main window can keep showing Windows setup progress without requiring the separate QEMU display to be frontmost.
- The runtime snapshot reports structured setup steps so the UI can show what is complete, blocked, or pending.
- The runtime snapshot reports preflight checks for installer media, guest OS, CPU, memory, and disk size. Installer media is required before Windows is installed; after the profile is marked installed, the ISO is no longer required for normal boot.
- Before installation, a profile becomes boot-ready only when installer media, virtual disk, shared folder, automatic install media, and preflight checks all pass. After installation, boot readiness is based on the installed system disk, shared folder, and non-installer preflight checks.
- Pressing Start in the macOS app builds the active local runtime plan and starts QEMU/HVF headlessly, then opens the live loopback RFB desktop in a reusable, resizable macOS window with native full-screen support. The launcher remains separate; set `VEIL_USE_NATIVE_QEMU_DISPLAY=1` only to opt into the temporary raw QEMU Cocoa fallback.
- Before installation, QEMU/HVF attaches the user-provided Windows ISO, the generated automatic install ISO, optional external driver media, and the writable NVMe system disk when starting the VM. After Windows is installed, Veil boots from the NVMe system disk and does not attach the Windows installer ISO. If the guest agent is already connected, Veil also stops attaching automatic install media. NVMe is used for the install-time system disk because the Windows 11 Arm installer sees it without a separate VirtIO storage driver. When external VirtIO driver media is configured, Veil automatically selects `virtio-net-pci` so one-click setup can establish guest networking; without driver media the boot-safe default remains `usb-net`. `VEIL_QEMU_NETWORK_DEVICE` can still explicitly select `e1000`, `e1000e`, `rtl8139`, `vmxnet3`, `virtio-net-pci`, or `virtio-net-device` for bounded live compatibility probes. The boot plan reports both `networkAdapter` and `networkDeviceArgument` so diagnostics show exactly which local NIC model was used.
- Windows gets a sound device. The QEMU/HVF plan attaches a CoreAudio backend plus Intel HD Audio (`intel-hda` with an `hda-duplex` codec, giving playback and capture), because Windows on ARM ships a native HD Audio class driver. `VEIL_QEMU_AUDIO_DEVICE=usb-audio` routes sound through the existing xHCI controller instead, and `VEIL_QEMU_AUDIO_DEVICE=none` removes audio entirely, which is the escape hatch for a locally built QEMU without CoreAudio support since QEMU refuses to start when an unavailable audio backend is requested. The selected device is reported in the typed runtime configuration summary's `audio` section.
- Apple Virtualization can still build a `VZVirtualMachine` with the same profile, ISO, automatic install media, and writable disk, but it is no longer the preferred visible-console path while Windows installer display support remains unproven.
- While the VM is running with native display fallback enabled, Open Recovery Display in the app menu or menu bar brings the active QEMU Cocoa window forward. In the default app path there is no second native display window, and the main VM screen does not expose a native-display control.
- While the VM is running and the guest agent is not connected, the host shell exposes an Install Guest Agent recovery action in the VM controls and menu bar. It sends the same bounded QMP/HMP key sequence as `veil-vmctl qemu-install-agent`, so a visible Windows desktop can run the `VEIL_AUTO` bootstrap without requiring the user to leave the app.
- While the VM is running, the host periodically retries the live guest-agent health check. When the Windows agent becomes reachable, Veil leaves demo mode and records guest-agent install evidence on the VM profile.
- The Windows app-window launcher accepts a Notepad open request before the live guest agent is connected, but stores it as a pending intent instead of showing demo mirroring. When the live agent connects, Veil sends the real launch request and opens the macOS mirror window from the accepted HWND.
- When a Windows app launch is queued and the local VM is already running without a live guest agent, the app shell now sends the same bounded attached-media `V.cmd` recovery path used by `veil-vmctl qemu-install-agent` once for that QEMU runtime. The reconnect poller then fulfills the pending app launch after `agent.health.response` is available, so the normal app path moves toward a Parallels-style "open app, recover runtime in the background" flow instead of leaving the user at a waiting state.
- The queued-app waiting state stays user-actionable: the main launcher play button changes to a guest-agent repair action and the menu bar shows Continue Queued App. Both use the same attached-media recovery path before the reconnect poller opens the mirrored macOS app window.
- The post-install launcher treats Open Windows App as the start of the app-open flow even before the live guest agent is connected. The UI can queue the selected app, show Agent as repair/waiting, and avoid claiming the agent is connected until a real `agent.health.response` arrives.
- Queued app launches that still need Windows start, guest-agent wait, or guest-agent repair no longer pass the release review gate. `openWindowsApp` stays actionable and points at the concrete start/repair/wait command, but review readiness only returns after the selected app can launch through a live connection or a mirrored macOS app window exists.
- If the local VM still reports `running` but the embedded console preview is stale or unavailable, app-runtime status reports `localRuntime.recommendedAction=recover-runtime-display` with `qemu-display-smoke` and `qemu-capture` recovery commands. This prevents the app-open path from treating a black/stale VM display as a healthy Parallels-style runtime.
- The same stale/unavailable preview also blocks the one-screen release gate: `windowsSetup` must point at Refresh Display until display evidence is current, so the app cannot report review readiness while the Windows surface may still be black or stale.
- A successful `qemu-capture` now stores `consoleScreenshotRefreshedAt` in the latest QEMU launch record. Follow-up app-runtime status polling preserves that refresh evidence, letting the launcher leave Refresh Display recovery once the console screenshot has been refreshed.
- If the VM is running with an old or missing `VeilAutoInstall.iso`, app-runtime status now reports `localRuntime.requiresGuestToolsMediaRebuild=true`, blocks `runtime.repairGuestAgentForApp`, and moves the one-screen primary action to `app-runtime-action --action stop-runtime`. After Windows stops, the same status carries the `veil-vmctl prepare --installer ...` rebuild command so the next boot attaches current guest tools before app connection repair.
- Rejected launch and wait-agent action reports follow the same rule: stale guest tools media next actions tell the operator to stop Windows, rebuild the attached media, refresh app-runtime status, and only then retry app connection repair.
- `veil-vmctl app-runtime-action --json --action recover-display` runs the same safe console refresh through the app-runtime action surface and returns `displayRecovery` evidence. The action is accepted only when the refreshed runtime evidence becomes `fresh`, so automation and future app controls cannot mark a black/stale display as recovered by accident.
- The app shell now exposes the same stale-display recovery as Refresh Display in the main play flow, the toolbar, the app command menu, and the menu bar. When display evidence is stale, app-open commands are gated behind that refresh instead of launching into a black or stale VM surface.
- `veil-vmctl app-runtime-action --json --action reconnect-restore` makes the Coherence restore loop explicit: if previous Windows app ids are persisted, automation can reconnect to the guest agent and restore their HWND-backed macOS windows through the same app-runtime action surface. A live retry on July 5, 2026 found the persisted Notepad intent but still returned `accepted=false` because the guest agent was unreachable, leaving `guest-agent-wait` and `veil-host-probe --diagnose-agent` as the next actions.
- `veil-vmctl app-runtime-action --json --action wait-agent --wait-seconds <n>` wraps the same post-install guest-agent readiness gate inside the app-runtime action surface. It returns `agentWait` with the forwarded endpoint, attempt count, host-forward probe, and recovery actions, and is accepted only when `agent.health.response` is reachable.
- `./script/build_and_run.sh --start-vm` launches the signed app bundle with the prepared profile and starts the VM automatically.
- Pressing Stop stops the active local VM process and closes host-side app bridge windows.
- Each Start attempt records a metadata-only boot report with timestamps, result, resulting runtime state, selected profile, planned devices, and error text when startup fails.
- Export Diagnostics writes a JSON bundle with host metadata, the runtime snapshot, setup steps, preflight checks, the stored VM profile, and the latest boot report to a user-selected diagnostics directory.
- Start requires a locally signed app bundle with the `com.apple.security.virtualization` entitlement.

The adaptive resource profile is an initial configuration policy, not live VM hot-resizing. The local runtime provider can use host memory on demand under the configured VM memory cap, and future work can add app-specific profiles, suspend/resume policy, and telemetry-driven adjustments once the real Windows path is stable.

Diagnostics bundles and boot reports are metadata only. They may include local file paths, VM device roles, runtime state, and startup error text so maintainers can understand setup state, but they must not copy Windows installer media, virtual disk bytes, product keys, or guest user data.

## Preflight Checks

Before the VM boot implementation lands, Veil already blocks obviously invalid profiles:

- Before installation, installer media must be a local bootable ISO file. VHD/VHDX files are treated as disk images, not installer media. After Windows is installed, this check becomes informational and the ISO may be removed from the normal profile.
- Guest OS must be `windows-arm64`.
- CPU allocation must be at least 2 virtual CPUs.
- Memory allocation must be at least 4096 MB.
- Disk size must be at least 64 GB.

These checks are deliberately conservative. They catch configuration mistakes before the local runtime provider tries to build or start a VM.

## Windows Display Reality Check

The v0.1 boot spike can create and start a `VZVirtualMachine`, attach ISO and disk storage, and open Apple's `VZVirtualMachineView`. That is not the same as a UTM-grade Windows installer path. Apple's public Virtualization documentation focuses on Linux and macOS guest flows, and Windows 11 Arm installer display/driver behavior through the Apple Virtio graphics path must be proven with real media before Veil can claim reliable Windows setup.

The QEMU/HVF compatibility spike has progressed past static planning: on July 1, 2026, a local Homebrew QEMU 11.0.2 install was validated with `qemu-system-aarch64`, Arm EDK2 firmware at `/opt/homebrew/share/qemu/edk2-aarch64-code.fd`, the user-provided `Win11_25H2_Korean_Arm64_v2.iso`, and a separate sparse QEMU test disk. The ISO contains `efi/boot/bootaa64.efi` and macOS reports it as an AArch64 EFI application.

Current QEMU boot evidence:

- QEMU can start the local device graph with HVF, Arm UEFI pflash code, a VM-local writable `uefi-vars.fd`, lock-safe read-only Windows ISO media, generated automatic install ISO media, writable raw NVMe system disk, NAT networking, Cocoa or headless ramfb graphics (virtio-gpu alone once the guest reports `viogpudo`), USB input, a local `swtpm` TPM 2.0 emulator, and serial logging.
- `veil-vmctl qemu-start --wait-seconds <n>` launches the stored Windows Arm profile with QEMU's display hidden behind a loopback VNC endpoint for Veil's embedded setup surface. It keeps an HMP monitor socket open for screenshots, attaches a QMP socket for structured key input on new launches, sends boot-prompt key input, and records both the VM-console screenshot path and loopback display endpoint. Use `--native-display` only for advanced recovery when the raw QEMU Cocoa window is needed.
- `veil-vmctl qemu-capture` refreshes the latest running QEMU launch screenshot through the recorded HMP monitor socket without sending a quit command, so the app and diagnostics can follow long Windows setup/OOBE runs.
- `veil-vmctl qemu-install-status --json` reads the current runtime snapshot and latest QEMU launch record into a metadata-only Windows install status report. It includes boot readiness, install evidence, automatic install media freshness, latest console screenshot path, latest display endpoint when available, planned 1440x900 guest framebuffer evidence, aspect-fit host-window scaling, Retina host-rendering policy, running QEMU process evidence when the configured disk is already attached, and safe next actions such as `qemu-display-smoke`, `qemu-capture`, `qemu-oobe-bypass`, or `qemu-install-agent`. It does not start, stop, copy, or modify Windows media or virtual disks.
- If `VeilAutoInstall.iso` is older than the staged `Autounattend.xml` or `Veil Guest Agent` bundle, install status reports `automaticInstallMediaStatus.state=stale` and moves the next action toward `qemu-powerdown`, `veil-vmctl prepare --installer ...`, and relaunch. This turns the common "repair still uses the old attached media" trap into a visible product diagnostic instead of a hidden operator memory.
- When install status detects a running QEMU process for the configured disk but no current launch record, it reports the process PID and any detected HMP/QMP socket paths before installer or preflight blockers. This protects the disk from relaunch attempts and makes the operator sequence explicit: close the existing Windows/QEMU PID, then reselect protected media or rerun readiness checks.
- The main Windows setup screen renders the same install-status next actions as compact recovery steps, so blocked setup states are visible in the app without requiring a terminal command.
- `veil-vmctl qemu-powerdown --wait-seconds <n>` requests ACPI shutdown through the recorded QMP socket on new launches, falls back to HMP for older launches, and waits for the recorded QEMU PID to exit. `qemu-start` now refuses to launch a second process while the latest recorded QEMU PID is still alive, protecting the Windows disk from accidental double attachment.
- If an older QEMU process is still alive but its launch record is missing or was written to an old diagnostics directory, Veil also scans running `qemu-system-aarch64` commands for the configured Windows disk path and blocks a new launch when the same disk is already attached.
- `veil-vmctl qemu-force-stop --i-understand-data-loss --wait-seconds <n>` is the last-resort local recovery command for a QEMU process that cannot be shut down through monitor control. It sends `SIGTERM`, records whether the PID exits within the wait window, and refuses to run without the exact risk acknowledgement flag.
- The main Veil app Start action launches the same local QEMU/HVF console path and opens its host-rendered desktop in an independent macOS window by default.
- The main Veil app Stop action now also checks the latest QEMU launch record and sends `SIGTERM` to a matching live QEMU PID for the current virtual disk, so CLI-started VMs can be stopped from the app instead of leaving the Stop control detached from the actual local runtime.

### Dynamic Resolution on virtio-gpu

Until November 2026 an installed Windows always drew through `ramfb` at a fixed 800 x 600, because Windows on Arm has no inbox driver for `virtio-gpu-pci`. On November 5, 2026 a scratch VM (its own raw disk, UEFI vars, and TPM state; the user's running VM was not touched) measured what changes with virtio-win's VirtIO GPU DOD driver. Setup: the bundled QEMU 11.1.3 with HVF (`hvf-arm-gicv3` plus `arm-gicv2m`), bundled EDK2 secure code, the Korean Windows 11 Arm 26300 ISO, virtio-win 0.1.302, `virtio-net-pci`, and a loopback VNC server. Each console was captured separately with QMP `screendump` and its `device` argument.

| Display devices | Firmware | Windows boot and sign-in | Desktop | RFB `SetDesktopSize` |
| --- | --- | --- | --- | --- |
| `ramfb`, `virtio-gpu-pci` (until now), no `viogpudo` | ramfb | ramfb | ramfb, 800 x 600, one monitor | ramfb console answers result 3 (invalid layout); Windows stays 800 x 600 |
| same, `viogpudo` installed | ramfb | ramfb | two extended monitors: ramfb 800 x 600 primary plus an unseen virtio-gpu monitor | not useful: VNC shows only the ramfb console |
| `virtio-gpu-pci` first, then `ramfb` | both consoles | ramfb; virtio-gpu black for about 25 s | two extended monitors | — |
| `virtio-gpu-pci` alone, `viogpudo` installed | virtio-gpu (EDK2 VirtioGpuDxe) | 6 to 9 s black, then the sign-in screen on virtio-gpu | virtio-gpu, one monitor | result 4 (forwarded); see below |

Findings:

- QEMU's VNC server shows the first graphic console. `ramfb` registers first, so Veil's VNC endpoint shows setup and BasicDisplay; `-vnc ...,display=<id>` and several `-vnc` servers with their own `id=` also work (`query-vnc-servers` lists them), but are not needed with the device policy below.
- `virtio-gpu-pci` alone cannot install Windows: EDK2's virtio GOP has no linear framebuffer for Windows' boot display, and WinPE has no `viogpudo`.
- `pnputil /add-driver viogpudo.inf /install` on a running Windows moves the desktop to virtio-gpu at QEMU's default 1280 x 800 without a reboot. With `ramfb` still attached, Windows then keeps both as an extended desktop. Cloning them fails (`SetDisplayConfig` returns 31, `ERROR_GEN_FAILURE`, since they are different adapters). `SDC_TOPOLOGY_EXTERNAL` keeps only the ramfb monitor and `SDC_TOPOLOGY_INTERNAL` only the virtio-gpu one; Windows stores that per pair of monitors, so it does not affect a boot on virtio-gpu alone.
- On virtio-gpu, `SetDesktopSize` gets result 4 ("request forwarded"): QEMU passes the size to the device, and `viogpudo` adds it to its mode list as its one custom mode, but neither the driver nor virtio-win's resolution service (`vgpusrv.exe -i`, which runs `viogpuap.exe` in the session) switched to it within 8 s for any of three sizes. `ChangeDisplaySettingsEx` to that size does, after which QEMU sends a server-side `ExtendedDesktopSize` (reason 0, result 0) with the new size.
- Measured through the rebuilt Windows agent's `display.resize.request`, from `SetDesktopSize` to QEMU's new-size rectangle: 1504 x 944, 2048 x 1280, 1440 x 896, 3024 x 1888, 1696 x 1056, and 1280 x 800 each took 0.1 to 0.2 s.
- While the Windows monitor was powered off (the scratch install had no `powercfg` step), forwarded sizes did not reach the mode list and `ChangeDisplaySettingsEx` answered `DISP_CHANGE_BADMODE`. The driver's private escape `VIOGPU_SET_CUSTOM_RESOLUTION` (what virtio-win's `viogpures.exe` sends) replaces the custom mode from a standard-user token. When Windows is already on the custom mode, the next custom size still answers BADMODE until another mode is committed; stepping through the smallest listed mode that covers the target worked in 14 of 14 trials. The agent does both only after a BADMODE, so the normal path is a single mode change.
- `viogpudo` pads the scanout width up to a multiple of 16 (1500 to 1504, 1512 to 1520, 1366 to 1376), so the host now aligns desktop sizes to 16 pixels instead of 8.
- QMP `x-query-virtio-status` on the virtio-gpu backend aborts QEMU 11.1.3 (`qapi-visit-core.c:52` assertion). Veil does not use it to detect the driver.

Retina: the host already asks for physical pixels (points times the backing scale factor), and 3024 x 1888 applied, but Windows stayed at 96 DPI (100%). `DisplayConfigGetDeviceInfo` reported the scale range as 100% recommended, up to 300%. Setting 200% changed the monitor to 192 DPI immediately and the taskbar to its normal size. The measurement set it through `DisplayConfigSetDeviceInfo` with a request type Microsoft does not document, so Veil does not use it; the supported path is Settings > System > Display > Scale, which the existing display-scaling status already recommends. Whether that choice survives every later resize was not measured.

What Veil does with this:

- The boot plan attaches `ramfb` plus `virtio-gpu-pci` for Windows Setup and for any Windows whose agent has not reported `viogpudo`, and `virtio-gpu-pci` alone after a cold start that found `capabilities.virtioGpuDisplay: true` in agent health ([protocol](protocol.md#health)). The choice is stored only when a cold start begins, so a suspended session resumes with the devices it was saved with. A later report of `false` moves the next cold start back to `ramfb`.
- New installs: the specialize pass installs NetKVM inline as before, then runs `Veil Guest Agent\scripts\Install-VeilVirtIODrivers.ps1` from `VEIL_AUTO`, which installs `NetKVM`, `viogpudo`, `viorng`, `Balloon`, and `vioserial` from `w11\ARM64` and logs to `%windir%\Temp\veil-virtio.log`. At first sign-in the bootstrap runs the same script's display step, which selects `SDC_TOPOLOGY_EXTERNAL` when Windows shows two displays. Measured on a second scratch install from the generated answer file: `viogpudo`, `viorng`, `Balloon`, and `vioserial` exited 0 (NetKVM 259, already installed by the inline step), the first session showed one 800 x 600 ramfb monitor, the rebuilt agent reported `virtioGpuDisplay: true`, and a cold start on `virtio-gpu-pci` alone came up at 1280 x 800 on one monitor and followed every size above.
- Existing installs: `Repair-VeilAgentConnectivity.ps1` runs the script for `viogpudo`, `viorng`, `Balloon`, and `vioserial`, then waits up to 15 s for the second monitor and keeps the ramfb one. Measured on the first scratch VM after removing `viogpudo` and clearing the Windows display database: the second monitor appeared about 1 s after `pnputil`, the script selected the ramfb monitor, and the next cold start on virtio-gpu alone came up at 1280 x 800. The full repair script, with its UAC prompt and agent restart, was not run in this pass.
- The first session after either path still shows 800 x 600; the size starts following the Veil window from the next cold start.

## Later Boot Flow

```text
Create or load VM profile
↓
Validate Windows installer, virtual disk, shared folder, and automatic install media
↓
Run profile preflight checks
↓
Create local runtime provider configuration
↓
Boot Windows 11 Arm
↓
Guide user through Windows setup when needed
↓
Mark Windows installed after the first desktop proof
↓
Install Veil guest agent inside Windows
↓
Reconnect host to agent through QEMU `hostfwd` at ws://127.0.0.1:18444
↓
Enable app launcher and coherence windows
```

After that first setup, the normal boot loop starts from the installed system disk and skips Windows installer ISO validation/attachment. The transition is automatic once the guest agent connects; before that, the host shell's Mark Windows Installed action or `veil-vmctl mark-installed` can record the same state after the desktop is visible.

## macOS Integration Requirements

- Shared folder starts narrow and user-visible.
- Clipboard sync is opt-in until loop prevention and data-type rules are tested.
- Dock and window integration should map Windows apps to macOS affordances without showing the Windows desktop as the primary interface.
- Guest paths must never be treated as trusted host paths.

## Non-Goals

- Bundling Windows media.
- Creating a licensed Windows installation for the user.
- Claiming Microsoft or Apple endorsement.
- Fully validating the contents or bootability of a Windows installer image before the VM boot spike proves the exact requirements.
- Copying Windows media, virtual disk contents, or product keys into diagnostics bundles.
